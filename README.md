# GPT × DSH 开发协作

双端本地插件：GPT 读取代码并生成实施文档，DSH 接收插件在桌面界面创建开发会话，完成后将代码和测试证据交回 GPT 审查。使用本机 Codex 登录与 DSH 模型配置，不额外接入 OpenAI API。

## 使用

在安装插件后的新聊天中输入：

> 用 dsh-gpt-workflow 处理 E:/Eworkspace 工作区中的这个需求：……。请自动识别相关仓库，GPT 先出实施文档，DSH 开发，完成后由 GPT 审查。

流程：`planned → running → awaiting_review → approved / needs_changes`。返工更新同一份实施文档，每轮创建一个独立 DSH 会话，保留全部历史。相同轮次重复投递不会重复创建会话。

DSH 右下角 **GPT** 按钮打开紧凑工作台（位于禅道按钮旁边），显示任务列表、状态与三步进度，可搜索任务/仓库、筛选进行中和待审查任务。点击任务卡片打开宽幅详情窗口，查看实施方案/开发结果/GPT 审查，并一键打开开发会话。详情不使用全屏遮罩，不禁用禅道等其他工作台；关闭按钮或详情内按 Esc 返回列表。面板打开时每 2.5 秒更新。

### 从 DSH 快速创建

1. 点击 **GPT → + 新建**，默认跟随 **DSH 当前会话所属工作区**，直接填写需求，无需选择子仓库。也可切到 **DSH 工作区 / Codex 工作区**，按名称或路径搜索已有工作区，或手动填写 `E:/Eworkspace` 等目录。没有当前会话所属工作区时提示选择，不猜测最近的演示项目。
2. 点击 **交给 GPT 规划并开发**。GPT 先只读识别需求相关的实际仓库，在同一条「GPT 协作 · 任务名称」聊天中继续生成实施方案，再由接收端派发 DSH。单仓库直接派发；跨仓库需求返回逐仓库方案并分别创建任务，共享原 GPT 规划聊天，分别审查。沿用 Codex 的登录和默认模型，不另存 API 密钥。
3. 面板显示规划、派发、开发与待审查状态。需求不足时显示待补充；失败详情包含原因，可「复用需求新建」后调整重试。重复点击/网络重试不重复派单。
4. DSH 完成后仍须 GPT 审查：详情中 **复制审查指令并打开 GPT**，将已复制的指令粘贴发送到原聊天，继续核对开发证据和提交审查。**打开 GPT 会话** 可随时查看方案记录。快速创建不会自动发送审查消息，也不会自动批准或 Git 收尾。

自动识别后，只检查相关仓库的未提交改动、任务锁和代码基线，无关仓库的改动不阻塞。GPT 返回工作区外的路径、伪仓库或在规划阶段扩大仓库范围时拒绝派发。无法定位功能时才向用户询问。单次最多 8 个仓库；任何目标不满足检查时不启动开发。多仓库派发不是跨进程事务，部分启动失败时保留已关联的全部任务并报告核查，不自动重放或回滚。接收端中断的请求保留待核查。识别和规划每阶段最长 10 分钟；记录在 `~/.dsh/gpt-workflow-receiver/requests` 和 `planning`。Windows 优先使用已安装 Codex 桌面执行器，也可用 `DSH_WORKFLOW_CODEX_BIN` 指定兼容的 `codex.exe`。会话启动后立即保存 ID，失败也保留定位入口；通过系统注册的 `codex://threads/<UUID>` 打开原聊天，不修改 Codex 数据库。

DSH 工作区来自宿主当前会话及工作区快照；Codex 工作区在选中该来源或点击刷新时通过 `project/list` 读取，只显示本机可访问目录。工作区是需求分析入口，DSH 的实际执行目录仍由 GPT 自动识别为具体 Git 根目录；不会在非 Git 主工作区根目录运行 Git，也不会迁移既有会话。旧版 `/projects` 目录接口仅保留兼容，新表单不再要求选子仓库。更新接口需在任务空闲时完整重启 DSH，旧宿主会提示重启而不发送不兼容请求。

“全部 / 进行中 / 待审查”统一使用 720px 高度（小窗口按可用高度缩减）；空列表、搜索无结果和加载状态均不改变面板高度，多任务在列表内部滚动。

四个详情页签（交接摘要、实施方案、开发结果、GPT 审查）均按 Markdown 渲染，支持标题、表格、代码块、列表、引用和行内代码。长内容可滚动，宽表格与代码块可横向滚动；原始 HTML 按文字显示，图片仅显示说明。前端更新后在 DSH 中按 `Ctrl+R` 加载。

从 Codex 发起时，GPT 在当前聊天保持等待并查询状态，完成后读取 diff、新文件和实际测试证据，记录审查结论。**关闭聊天后 DSH 可以继续运行，但此版不会自动唤醒 GPT**；重新打开聊天，让 GPT 查询并继续即可。只有审查通过，GPT 才按目标仓库规则统一 Git 收尾。

### 任务交接与续接

借鉴 Trellis 的明确任务入口、按用途引用上下文和阶段接力；沿用一份实施方案，由程序自动保存交接材料，无须创建 Trellis 任务或填写额外表单。

- GPT 方案：代码依据写“文件/规范 + 用途 + 开发/审查阶段”；验收用稳定编号 A1、A2…，附观察方法；测试写工作目录、命令及环境前提。
- 派发时：每轮 `runs/<轮次>/` 保存 `handoff.json`、`交接摘要.md` 和冻结的 `实施方案.md`，附仓库、Git 基线、方案指纹及上一轮审查。DSH 从明确的 Active task 入口读取；引用不可读时记录限制，不自行更改权限。
- DSH 回传：固定五节“已改文件、验收结果、测试记录、未完成与阻塞、交回 GPT”，分别记录未满足/未验证项、真实测试退出码和下一步。完成时生成 `开发交接.md`；程序检测到的文件变化与 DSH 自述分开展示。报告齐全不代表测试通过，缺项不猜测补齐。
- 新聊天接手：`workflow_list` 找到任务 → `workflow_handoff` 读取接手方、下一步、验收及返工依据 → `workflow_status` 核对最新状态。面板默认打开“交接摘要”，支持复制给新聊天；复制内容只是当时的快照，不自动启动或发送消息。
- 返工：继续同一任务，使用 `workflow_revise` 更新方案，再 `workflow_start` 开始下一轮。新交接引用原审查和上一轮目录，旧轮次保留。中断时先核查原会话，不重放、不自动解锁。

旧任务兼容原方案/结果；没有交接包时会明确提示。新增 MCP 工具需更新 Codex 插件后在新聊天加载；DSH 后端更新需空闲时完整重启。本轮代码验证范围见 [验证记录](docs/验证记录.md)。

## 从禅道一键交给 GPT

两端插件同时安装更新后，在 DSH 空闲时完整退出再启动（仅 Ctrl+R 不会加载新增宿主接口）。

1. 打开目标 DSH 工作区会话，在禅道任务 / Bug / 需求旁点击 **交给 GPT 开发**。默认跟随当前工作区，也可在禅道的发送目标下拉中明确选择。
2. 程序先读取完整正文和附件引用，交给 GPT 定位实际仓库、制定方案，再派发 DSH。附件只带同一禅道服务器的无凭据路径引用，不自动下载；相关仓库仍须满足原有干净基线检查。
3. 已关联条目显示 **查看 GPT 进度**，自动打开该协作记录。两边区分开发中、待 GPT 审查、审查通过；GPT 详情可打开原禅道条目及已关联的 GPT / DSH 会话。

同一服务器＋条目类别＋编号只关联一个请求，重复点击、网络重试、标题变化和重启都回到原记录。失败、中断或待补充时也不自动重派；在原 GPT 会话补充信息或核对任务后续接。原请求的工作区和需求快照保留，多仓库必须全部审查通过才显示通过。此版没有直接修改或重建关联的按钮。

此入口不自动开始、完成、指派或回写禅道任务；禅道原有「处理」动作仍保留原行为。关联进度仅在禅道面板打开且已登录时查询当前标签前100条；其他条目点击时单独查找，不受最近100条协作列表限制。缺少插件/旧宿主会提示安装、启用或重启，不会降级成重复派单。

## 本地安装

要求 Node.js 22+、Git、已完成模型配置并保持运行的 DSH 桌面版。已实测桌面版 `0.2.0-rc.2`；使用原生宿主服务，DSH 升级后应复测。

```powershell
cd E:/Eworkspace/dsh-gpt-workflow
npm ci
npm test
npm run build
# 使用桌面安装附带的 CLI，避免 PATH 中旧版 CLI 操作 desktop profile。
& "$env:LOCALAPPDATA/Programs/DeepSeek Harness/resources/runtime/cli/bin/dsh.cmd" plugin --profile desktop add E:/Eworkspace/dsh-gpt-workflow/dsh-receiver
codex plugin marketplace add E:/Eworkspace/dsh-gpt-workflow
codex plugin add dsh-gpt-workflow@dsh-gpt-local
```

构建输出分别是 `.runtime/plugin`（Codex）与 `dsh-receiver/lib`（DSH）。本地 link 安装后须保留源码仓库与构建目录。升级 DSH 插件后，在没有运行中任务时完整重启 DSH；Codex 通过受支持的安装命令更新缓存，不手动改缓存。

```powershell
codex plugin add dsh-gpt-workflow@dsh-gpt-local
```

安装后新开聊天加载 Skill 和 MCP 工具。如工具尚未加载，可运行 `node src/cli.mjs <动作> <参数.json>`；安装包对应 `dist/cli.mjs`。动作和参数对应下表的工具名（去掉 `workflow_` 前缀）；`-` 表示从 stdin 读 JSON。

## 工具

| 工具 | 作用 |
| --- | --- |
| `workflow_create` | 保存 GPT 实施方案，记录仓库、分支和代码基线 |
| `workflow_start` | 检查 DSH 接收端在线，取得仓库锁并向桌面派单 |
| `workflow_status` / `workflow_list` | 查询与跨聊天续接 |
| `workflow_handoff` | 只读获取当前接手方、下一步、交接摘要、返工依据和报告缺项 |
| `workflow_result` | 返回 DSH 说明、退出码、代码快照、差异及工具事件路径 |
| `workflow_review` | GPT 根据证据提交通过或返工结论 |
| `workflow_revise` | 修改方案并准备下一轮开发 |
| `workflow_recover` | 监督进程异常消失后，向接收端确认开发结束再恢复 |

实施文档要求五个 `##` 标题：目标与范围、代码依据、实施步骤、验收标准、测试要求。模板在 `skills/dsh-gpt-workflow/references/实施方案模板.md`。

## 状态与运行边界

- 初次任务只接受干净、已有提交、处于命名分支的具体 Git 仓库；不会自动提交、stash 或清理既有改动。需要保留他人改动时使用独立工作树。
- 创建和启动之间会核对基线；审查结论必须绑定最新证据哈希和当前代码快照。
- 锁覆盖插件内同一仓库的开发及待审查阶段；它是协作锁，不能阻止外部编辑器、其它工具或不遵从指令的模型写文件，也不是操作系统沙箱。
- DSH 只开发，Git 收尾交给 GPT；检测到 DSH 提交或切分支则标记失败并保留证据。
- 每轮单独保存提示词、实施文档、工具事件、最终回答、退出码、diff 和未跟踪文件哈希。忽略的文件不纳入 Git 证据；审查者仍需核对任务要求及真实运行环境。
- 不保存模型 thinking 事件。运行日志可能含代码和工具输出，仅保存在本机用户目录，勿提交到共享仓库。
- 默认最长执行 30 分钟，超时只取消本次 DSH 会话并等待空闲，不终止桌面应用。监督进程异常、连接不明或宿主重启后的 `interrupted` 均保留锁；不会自动重放。此 MVP 对宿主中途重启需人工核对原会话。
- MCP 客户端断开不终止独立 worker。进程退出成功仅表示待审查；测试失败、环境缺失或需求阻塞仍需 GPT 根据报告决定。
- 审查结论先可靠保存在 GPT 端，再同步到 DSH 面板。同步失败会返回 `reviewDelivery: pending...`；重试完全相同的 review 参数可补发，不重新批准或开发。
- 接收端只监听 `127.0.0.1` 随机端口，使用随机令牌，并拒绝浏览器 Origin。令牌与接收记录位于 `~/.dsh/gpt-workflow-receiver`，不进入源码或输出。面板使用带专用标头及来源校验的 DSH 同源接口，可读取列表、提交快速需求和打开已关联 GPT 会话，不能直接批准任务。
- 暂不支持跨机器派单、多任务并行写同一仓库、自动唤醒关闭的聊天或无人值守 Git 推送。

## 可选环境变量

| 名称 | 默认 / 含义 |
| --- | --- |
| `DSH_WORKFLOW_HOME` | `~/.codex/dsh-gpt-workflow`，任务持久目录 |
| `DSH_WORKFLOW_WORKSPACE_ROOT` | `E:/Eworkspace`，仅旧版项目列表兼容接口使用；新表单默认跟随 DSH 当前工作区 |
| `DSH_WORKFLOW_RECEIVER_FILE` | 可选：接收端连接文件绝对路径，默认 `~/.dsh/gpt-workflow-receiver/connection.json` |
| `DSH_WORKFLOW_BIN` | 兼容模式：显式设置后使用旧 headless 路径，主要用于离线测试；正常桌面模式不要设置 |
| `DSH_WORKFLOW_PROFILE` | 仅旧 headless 兼容模式使用，默认 `headless` |
| `DSH_WORKFLOW_TIMEOUT_MS` | `1800000`，每轮超时，允许 1000～86400000 |

认证沿用本机 DSH 配置；不要在参数、实施文档或插件文件中写入密钥。新开发会话采用 `workspace-write`，权限申请留在 DSH 原生界面处理，插件不会自动批准提权。

Windows 若出现 `SetNamedSecurityInfoW ... grantWrite`，先确认具体仓库 ACL。可用 `scripts/repair-windows-acl.ps1 -Repo <仓库绝对路径> -BackupFile <新的备份文件绝对路径>`：只对当前用户拥有的 Git 根目录补充 `TakeOwnership`，备份原 SDDL，不递归、不改所有者。此操作只解决目录标签权限，**不能消除受限沙箱的子进程管道 `spawn EPERM` 限制**。测试命令仍须按实际结果判断，不能把完全权限下的通过记成受限沙箱通过。

## 验证

`npm test` 验证鉴权、持久化去重、失败/中断、审查同步、桌面传输、仓库锁、修订和 MCP 通信，不调用模型。真实冒烟需显式运行（会使用 DSH 额度）：

```powershell
node scripts/smoke-real.mjs E:/Eworkspace/.tmp/某个不存在的演示目录
```

脚本创建独立示例仓库，让真实 DSH 编写标签规范化函数与测试。它只启动开发，审查必须读取证据后由 GPT 完成。

脚本支持 `--prepare`，只创建干净仓库和方案，便于先核对环境，然后使用 CLI start 派单。具体真实验证及剩余限制见 `docs/验证记录.md`。

## GPT 规划回复与暂停原因

GPT 会话以中文 Markdown 显示仓库定位依据、实施方案或待补充问题；程序通过 `submit_planning_result` 接收结构化数据，不再把 JSON 当成最终回复。定位与规划继续使用同一可见会话。结果必须匹配当前会话、回合和阶段；缺少工具交接或模型执行失败时不会派发 DSH。

定位阶段会在 GPT 最终回复前预检查目标仓库。未提交改动、仓库占用等原因会反馈给 GPT 说明；通过预检查后，外围程序仍会冻结并复核代码基线。任务详情的“实施方案”页优先显示当前暂停原因，再显示原需求。定位成功只表示找到仓库，不代表已完成方案或启动开发。

该接口使用本机 Codex App Server 的实验性动态工具协议（[官方文档](https://learn.chatgpt.com/docs/app-server)）；需要支持 `thread/start.dynamicTools` 和 `item/tool/call` 的版本。升级接收插件后请在空闲时完整重启 DSH。历史 JSON 消息不会被改写，已失败或待补充的请求不会自动重跑；先处理原请求的阻塞，再通过明确的新请求继续。
